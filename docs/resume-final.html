我的工作
  • 权限（核心）：把「角色」在业务层一次性投影成 ACL（员工 → 公开；人事 → 人事 + 公开；未登记角色直接 403、不降级）， 算法层只认 ACL 不认用户。实测同一问题：人事命中薪酬条款并带出处，普通员工被明确拒绝； 而普通员工问「年假」能正常回答 —— 差别只来自账号角色，请求参数一个字没变。
  • 检索效果：向量 + BM25 双路召回 + RRF 融合 + LLM 精排；把条款号写进索引文本后， 条款类问题命中 2/15 → 13/15（同 32 题配对对照，保留回滚开关，出问题可一键退回）。
  • 成本保护：每日配额在调用大模型之前判定（Redis 计数 + 按天过期），超限返回 429 并给出重试时间， 超额请求不产生任何模型费用；问答、拒答、超限三类决策全部落审计表。
  • 质量判定：改动是否真的变好，用调参集之外的 105 题独立集 + 配对显著性检验判定，不看单次分数的涨跌； 另有三条「看起来更好」的改法被同一门禁否决、全部没上。
项目难点
  • 权限要穿过两层，最容易漏在「哪一层」：检索在 Python、身份在 Java，两边各判一次迟早有一层漏。 解法是只保留一处转换，未知角色直接拒绝而不是降级 —— 宁可拒绝，也不要猜。
  • 模型故障不能被伪装成「库里没有」：精排返回非法内容时如果按 0 分处理，会触发一条平平无奇的拒答， 故障就被永久掩盖。改成抛错并记录原始返回，只有分数确实低才拒答，降级时在响应里标记。
