PolicyDesk：制度文档的多步检索 Agent（独立开发）2026.09 – 2026.11

项目背景：制度散落在几十份文档里，员工查一次要翻很久；通用大模型回答没有出处、容易编。 产品：Agent 自己决定查几次、查什么，答案给原文条款，查不到就明确拒答，前端时间线显示每一步。
Vue 3 + TypeScript ｜ Spring Boot 3 + MySQL 8 + Redis ｜ Python + FastAPI + bge-small-zh / BM25 / RRF / DeepSeek ｜ MCP + SSE ｜ Docker Compose
项目详情
  • 工具调用：循环手写为 for rnd in range(rounds_limit)（默认 6 轮）， 模型选工具 → 执行 → 结果回填；工具走 MCP（JSON-RPC 独立进程），参数按 schema 校验， 失败按超时 / 参数 / 权限归因；另用 LangGraph 重写做对照，控制流只差 3 处。
  • 拒答与检索：以原问题的过闸结果为准，改写问法命中无关条款也不推翻（26/61 → 40/61）； bge-small-zh 向量 + BM25 + RRF + 精排，上下文八层 + token 预算 + trace，多轮保留最近 3 轮。
  • 受限执行与流式：容器内跑代码（断网 / 只读 / 限内存 / 限进程，四类越界都实测拦截）； SSE 穿过 FastAPI 与 Spring Boot 两层，前端按事件渲染时间线，16 条单测钉住「算不算成功」。
  • 评测与交付：105 题盲出集 + 9 套件 / 156 用例，先量噪声地板再上 exact McNemar； Docker 五容器 + Nginx + Tunnel，CI 覆盖后端 / 前端 / 容器 / 评测。
成果：gold 条款命中 42/44 · 拒答 40/61 · 与同刻 /chat 打平（1 胜 2 负，差异在噪声带内）
一次问答约 5 秒、2 步工具调用 · 测试 67 条后端 + 16 条前端 + 548 条算法层

AI 发布门禁平台（独立开发）2026.11

项目背景：改一版 prompt / 换一次模型之后，"线上会不会变差、最近改了什么、出事怎么退"三件事答不出来。 产品：配置版本化 → 灰度发布 → 自动跑评测门禁 → 不达标自动回滚，全过程可审计。
Spring Boot 3 × 3 服务 + Python 执行器 ｜ MySQL（每服务独立库）｜ Redis Streams / outbox ｜ JDK HttpClient
项目详情
  • 服务拆分：配置 / 发布 / 门禁三个服务各自独立库（读多写少 vs 事务写 vs 长任务，故障域不同）； 跨服务调用带超时且 fail-closed（版本校验不通过就不许发布）。
  • 并发与幂等：版本号用发号器表原子分配（30 并发零重号）；状态迁移用 rev 乐观锁（过期 rev → 409）； outbox + Redis Streams 至少一次投递，消费端唯一索引去重（同一事件投 100 次只建 1 个任务）。
  • 灰度与门禁：SHA-256 稳定分桶（同租户 1000 次结论一致，并用 Python 独立实现交叉验证）； 门禁真跑 20 题评测（18/20），不达标自动回滚；回滚是指针原子切换，而非重新发布。
工程数据：/api/gray 约 2000 rps、p95 15ms · traceId 跨 4 进程可串 · 执行器宕机时任务不丢、恢复自愈
