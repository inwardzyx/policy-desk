我的工作
  • Agent 循环：手写 for rnd in range(6)（不套框架 —— 框架会把"为什么硬答"藏进回调）， 每轮「模型决定调哪个工具 → 执行 → 把结果放回消息序列」；工具走 MCP，本机另起进程用 JSON-RPC 通信。
  • 全链路与流式：Vue → Spring Boot（JWT / 配额 / 审计）→ FastAPI，SSE 穿透两层： Java 只搬字节不解析，事件语义只在 Python 一处定义；超预算/撞上限都会显式收尾，不静默截断。
  • 时间线：按后端事件渲染每一步（工具 / 参数 / 耗时 / 命中数），失败标红； 16 条前端单测钉住"算不算成功"的判据 —— 缺 result 事件即判「状态未知」，不许显示成成功。
  • 质量门禁（差异化）：用 105 题盲出独立集判定 agent 有没有变差（先量噪声地板，再上 exact McNemar）； 实测抓出并修掉一条真实退化：改写问法就能绕过拒答，拒答 26/61 → 40/61（`/chat` 同刻 41/61）。
两个难点
  • 「拒答」不能由循环里最后一次查询决定：改写成"退学 复学 重新入学"后命中了《应征入伍管理办法》， 答案看起来有出处、其实无关。改成以原问题过闸为准，循环里查到什么都不能推翻它。
  • 改写重试差点误杀正常题：第一版按"每次调用"数上限，正常题第一次换措辞就被截断 —— 改成按"新的不同问法"去重计数才既不放过绕闸、也不打断正常多步检索。
结果
  • gold 条款命中 42/44（同一刻 /chat 41/44），拒答 40/61；一次问答约 5 秒、2 步工具调用。
  • 63 条后端 + 16 条前端 + 473 条算法层测试，每次提交自动跑；五容器一条命令起，公网可访问，两仓 CI 全绿。
