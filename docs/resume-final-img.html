我做了什么
  • 循环是手写的 for rnd in range(rounds_limit)，默认 6 轮。没套框架，因为框架会把 模型"为什么硬答"的过程藏进回调里，不好查。每轮就是模型选工具、执行、结果放回消息序列； 工具走 MCP，单独起进程用 JSON-RPC 通信。另外用 LangGraph 把同一个循环重写了一遍做对照， 比下来只换掉了控制流的三处。
  • 上下文分八层拼装，带 token 预算和 trace；超预算或撞上限时显式收尾，不静默截断。 SSE 要穿过 Java 和 FastAPI 两层，Java 只搬字节不解析，事件语义只在一处定义。
  • 前端时间线按后端事件渲染，用 16 条单测覆盖"算不算成功"：缺 result 事件就显示"状态未知"， 不会画成成功。
  • 评测在 105 道盲出题上做：先量噪声地板，再上 exact McNemar。它抓到过一次真实的退化， 改写问法能绕过拒答，修完拒答从 26/61 到 40/61（同刻 /chat 是 41/61）。
两个踩过的坑
  • 拒答曾经由"最后一次查询"决定：模型把问题改写后命中无关条款，答案看起来有出处。 后来改成以原问题过闸为准，循环里查到什么都不推翻它。
  • 报告自己会过期：报告头记了代码、语料、依赖、判据四个版本。报告过期是正常的， 引用过期报告才该报错。

工作习惯

  • 简历里的测试数有脚本现算（scripts/check_resume_numbers.py），对不上就失败， 不靠手写。
  • 写检查之前先想清楚它在坏情况下会不会响，每条都配一个变异用例，先看它红过。
  • 交接的东西都入库：HANDOFF、决策记录、盲审记录；报告头记四个版本。
