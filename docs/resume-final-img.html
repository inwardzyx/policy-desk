我的工作
  • Agent 循环与工具：手写 for rnd in range(6)（不套框架 —— 框架会把"为什么硬答"藏进回调）， 每轮「模型选工具 → 执行 → 结果放回消息序列」；工具走 MCP，另起进程用 JSON-RPC 通信； 另用 LangGraph 重写同一循环做对照，量出"换框架只换掉了控制流三处"。
  • 上下文与流式：上下文八层 + token 预算 + trace，超预算 / 撞上限都显式收尾，不静默截断； SSE 穿透 Java 与 FastAPI 两层 —— Java 只搬字节不解析，事件语义只在一处定义。
  • 前端时间线：按后端事件渲染每一步（工具 / 参数 / 耗时 / 命中数），失败标红； 16 条前端单测钉住"算不算成功"的判据 —— 缺 result 事件即判「状态未知」，不许显示成成功。
  • 质量门禁（评测）：用 105 题盲出独立集判定改动有没有让 Agent 变差（先量噪声地板，再上 exact McNemar）； 实测抓出并修掉一条真实退化：改写问法就能绕过拒答，拒答 26/61 → 40/61（同刻 /chat 41/61）。
两个难点
  • 拒答不能由"最后一次查询"决定：它把问题改写后命中了无关条款，答案看起来有出处。 改成以原问题过闸为准，循环里查到什么都不能推翻它。
  • 判据本身也会过期：报告头记四个版本（代码 / 语料 / 依赖 / 判据）；报告过期合法， 引用过期报告才报红。
结果
  • gold 条款命中 42/44（同刻 /chat 41/44）、拒答 40/61；一次问答约 5 秒、2 步工具调用。
  • 63 条后端 + 16 条前端 + 473 条算法层测试；五容器一条命令起、公网可访问，两仓 CI 全绿。
