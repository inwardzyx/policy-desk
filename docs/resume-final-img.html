AI 发布门禁平台2026.11

项目背景：问答类应用的迭代很轻——改几句话术、换一版模型就是一次发布，但发布后三件事答不出来： 有没有变差（没有上线前量化对比，只能等用户抱怨）、最近改了什么（配置散在代码和 .env 里，没有版本号）、 出事怎么退（手工改回去或重新发旧代码）。
产品：配置版本化 → 灰度发布 → 自动跑评测门禁 → 不达标自动回滚，全过程可审计。
Spring Boot 3 × 3 微服务 + Python 执行器 ｜ MySQL（每服务独立库）｜ Redis Streams / outbox ｜ JDK HttpClient ｜ Docker Compose
项目详情
  • 微服务拆分：配置 / 发布 / 门禁三个服务各自独立库（读多写少 vs 事务写 vs 长任务，故障域不同）； 跨服务调用带超时且 fail-closed——版本校验不通过就不许发布，而不是"猜它存在"； 不用注册中心 / Gateway（三个服务、地址固定，用不上）。
  • 并发与幂等：版本号用发号器表原子分配（30 并发零重号，第一版 MAX(version)+1 有 19/30 撞唯一键）； 状态迁移用 rev 乐观锁（过期 rev → 409，不是 500 也不是静默成功）； 建任务按 event_id 唯一索引幂等（同一事件投 100 次只建 1 个任务）。
  • 灰度与回滚：SHA-256 稳定分桶（同租户 1000 次结论一致，并用 Python 独立实现交叉验证桶号）； 回滚 = current_release 指针原子切换（O(1)、幂等），而不是重新发布旧版本—— 重新发布要再走一遍校验与门禁，慢且可能失败。
  • 异步链路：发布与"门禁该跑了"在同一事务里写 outbox，后台扫表投递到 Redis Streams（至少一次）， 消费端先处理成功再 ack；执行器宕机时发布照常成功、任务不丢，恢复后由扫描器重投自愈。 真评测要 20–80 秒，据此把"提交失败"与"还在跑"分开（前者 5 秒重投，后者 300 秒租约）。
  • 门禁判定：评测真实跑（20 题均匀抽样，18/20 = 0.90，两次一致），不达标自动回滚、通过则保持 CANARY 等人放量； 阈值由发布方自己声明（改 prompt 与换模型风险不同，写死一个全局标准说不清"为什么放行"）； 结果回写幂等（同一 job 回调 3 次只生效一次，避免把指针再推一格）。
  • 状态机与审计：四态 PENDING → CANARY → FULL → ROLLED_BACK，规则收在枚举一处（非法迁移拒绝、回滚后不可复活），每次迁移留 operator / 时间 / 分数。
  • 可观测与工程化：traceId 随事件跨 4 个进程可串（异步靠事件体携带、不靠线程）；一条命令 docker compose up 起门禁平台六容器；16 条单测 + 变异测试（改坏三处实现全部变红）。
成果：/api/gray（每请求都要调的热路径）约 2000 rps 饱和、16 并发内 p95 15ms； 11 条端到端判据全绿 · 执行器宕机时任务不丢、恢复后自愈 · 单次门禁 20 题 / 78 秒
