项目经历

制度问答台 —— 面向企业制度的可核验问答系统个人项目 · 2026.09 – 2026.11

把 10 份制度文档做成「答案带条款出处、库里没有就当场拒答」的问答系统，按 「谁在问、能问什么、问了多少次」拆成 Java 业务层与无状态算法层 —— 算法层不认识「用户」、只认 ACL。
个人工作
  • 拆层与配额：算法层（检索 / 精排 / 生成）与业务层（用户 / 角色 / 配额 / 审计）解耦， 同一套检索可被不同业务复用，也能脱离数据库单测； 配额放在调用模型之前判定，超额请求零 token 消耗（429 + Retry-After）。
  • 权限（核心）：角色 → ACL 单向投影，身份只解析一次、下游只认 ACL。 实测同一问题：hr 命中「加班与补贴」并带原文引用，employee 明确拒答； 而 employee 问「年假」可正常回答 —— 差别只来自令牌里的角色。
  • 检索：向量 + BM25 + RRF 融合 + LLM 精排；把条款号写进索引文本后， 条款类问题 2/15 → 13/15（同 32 题配对实验，保留回滚开关）。
  • 评测：双评测集（调参集 + 105 题盲出独立集，零重合），用 exact McNemar 判定改动是否真有效 （p = 0.0156）；另有三条「看起来更好」的改法被同一门禁否决、全部不动。
  • 交付：63 条后端测试（H2，不依赖本机 MySQL）+ 4 条前端测试 + CI 三 job； Compose 编排五容器，问答端到端 ≈ 4.0 s，检索 p50 3.1 ms。
项目难点
  • 权限要穿过两层，最容易漏在「哪一层」 —— 检索在 Python、身份在 Java，每层各判一次迟早有一层漏。 解法：只保留一处转换（角色 → ACL），未登记角色直接 403、不降级（宁可拒绝，不要猜）。
  • 入库「该拦的」和「不该拦的」分不开 —— 固定阈值 0.9 误杀合法条款、0.99 又放过同义改写。 解法：先量出两簇的真实分布（最像的合法对 0.9230、该拦的改写 0.9839，中间是空的）， 据此定 0.96；286 块放行 263 / 拦 23，每条理由可逐条查。
  • 故障不能被伪装成「库里没有」 —— 精排返回非 JSON 时若给全 0 分，会触发一条平平无奇的拒答， 故障被永久掩盖。解法：抛错并记录原始返回；只有精排 < 5 分才拒答，降级时标 rerank_used=false；审计只存问题的 SHA-256（可比对频次、还原不出原文）。
